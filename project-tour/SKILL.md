# Project Tour

Create one evidence-backed, conversational tour that gives the reader a mental model of the project before explaining its files.

## Establish the scope

1. Treat the repository root as the project root. Use the current working directory when no repository root exists.
2. Honor repository instructions such as `AGENTS.md` or `CLAUDE.md`.
3. Use a user-specified application, package, or subsystem as the scope when provided.
4. In a monorepo, infer the intended application from the request and current working directory. Ask one concise scope question only when multiple unrelated applications remain equally plausible.
5. Target a 10–15 minute listen unless the user requests a shorter, longer, or focused tour.

## Investigate before writing

Build the explanation from implementation evidence, not from documentation alone.

1. Inspect the repository structure without reading dependency, cache, generated, binary, coverage, or build-output directories.
2. Read relevant instructions, READMEs, architecture documents, package manifests, lockfiles, task runners, container and deployment configuration, and framework configuration.
3. Locate every meaningful entry path, including CLI commands, servers, workers, scheduled jobs, development studios, notebooks, and test harnesses.
4. Trace at least one representative journey from its entrypoint through orchestration, state or data changes, external calls, persistence, and returned output.
5. Inspect configuration schemas, defaults, environment-variable examples, and variable lookups. Never reveal values from `.env` files, credential stores, private keys, tokens, or other secrets.
6. Read tests that clarify intended behavior, boundaries, failure handling, and common usage.
7. Identify the important components, their responsibilities, and the interfaces between them.
8. Compare documentation claims with active code and configuration. Prefer current implementation evidence for runtime behavior and record meaningful conflicts.

Keep an internal evidence model:

- **Verified:** directly supported by code, configuration, tests, or runnable commands.
- **Inferred:** strongly suggested by naming or structure but not conclusively established.
- **Unknown:** missing, ambiguous, unreachable, or contradictory.

Do not turn an inference into a fact. Do not claim that a command works merely because it appears in documentation.

## Protect existing work

Use `PROJECT_TOUR.md` at the project root.

- If the file does not exist, create it.
- If it contains `<!-- Generated by project-tour; safe to refresh. -->`, replace the complete file.
- If it exists without that marker, ask before overwriting it.
- Do not add a timestamp; keep refresh diffs meaningful.
- Do not modify any other project file.
- If the repository has too little evidence for a useful tour, explain what is missing and do not create a misleading placeholder.

## Write the tour

Start the file with a descriptive title followed immediately by:

`<!-- Generated by project-tour; safe to refresh. -->`

Write in present tense as a knowledgeable guide speaking directly to the reader. Prefer connected paragraphs over tables and inventories. Introduce technical terms before relying on them. Keep exact commands in fenced code blocks. Mention paths and symbols naturally, without overwhelming the narration with line numbers.

Use these sections in this order, adapting their titles to the project:

1. **The mental model** — Give a short, spoken-style overview of what the project does and how its main pieces fit together.
2. **How you start it** — Explain each verified entry mode, its prerequisites, and where execution begins. Distinguish production and development paths.
3. **One journey through the system** — Narrate one concrete end-to-end scenario in causal order: “When you run…”, “This calls…”, “The state then…”.
4. **The main components** — Explain responsibilities and collaboration boundaries, grouping files by purpose rather than listing them alphabetically.
5. **State, data, and external services** — Explain important state shapes, transformations, persistence, APIs, queues, models, or other integrations.
6. **Configuration** — Explain user-configurable variables, known defaults, where they are read, and the behavioral effect of changing them. List names only, never secret values.
7. **The important files** — Provide a selective responsibility-based map of the files needed to navigate the codebase.
8. **Common changes** — Explain where a maintainer would go to make the most likely changes, without pretending to implement them.
9. **How you verify and debug it** — Include supported tests, checks, logs, tracing tools, and failure paths that the evidence establishes.
10. **Conflicts, uncertainties, and coverage gaps** — Clearly label documentation drift, inferences, unknowns, uninspected areas, and commands that were found but not verified by execution.
11. **Source trail** — End with a compact list of the key file paths and symbols used as evidence.

Omit a section only when it is genuinely inapplicable; state “Not established from the repository” when the topic matters but evidence is missing. Keep secondary flows brief so the main runtime story remains easy to follow by listening.

## Finish

Re-read the tour for causal continuity, secret leakage, unsupported certainty, and unexplained jargon. Confirm that every important runtime claim can be traced to the source trail. Then tell the user where `PROJECT_TOUR.md` was written or refreshed and summarize any important uncertainty or documentation conflict.
